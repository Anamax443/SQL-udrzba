1. Nový klíčový nález: riziko se materializovalo

CSV export obsahuje 286 událostí SQL Server Error 9002 se zprávou:

The transaction log for database 'NAV-LIVE' is full due to 'LOG_BACKUP'.

Události jsou soustředěny od 2026-08-10T03:33:18.606000Z do 2026-08-10T03:34:32.156000Z. To už není hypotéza o možném zaplnění logu. Je to doložený produkční incident.

Dopad na klasifikaci: Fáze 0 už nemá být popisována pouze jako prevence. Jde o nápravné opatření po prokázaném incidentu způsobeném stavem LOG_BACKUP.

2. N1 — souběžné log backup joby

BLOKUJÍCÍ PROVOZNĚ Závěr dokumentu je správný: staré joby Tlog a Tlog2 nesmějí dlouhodobě běžet současně s novým 24/7 jobem do různých cest.

Formulace „rozštěpí řetěz“ je ale technicky příliš hrubá. SQL Server udržuje jednu LSN posloupnost. Souběžné joby mohou vytvářet jednu posloupnost log backupů rozdělenou mezi více médií. Správný termín je spíš fragmentace restore chainu mezi několik nezávisle spravovaných sad souborů.

VýrokHodnocení
Více jobů do různých míst komplikuje restoreSprávně
Cleanup jedné větve může znemožnit restore přes daný LSN úsekSprávně
Samotné vypnutí jednoho ze souběžných jobů automaticky vytvoří LSN díruNe nutně; pokud jiný job dál korektně zálohuje log, LSN chain pokračuje
Alert jen podle backupset může být falešně zelenýSprávně

3. N2 — pevný soubor a CONTINUE_AFTER_ERROR

N2a: jeden rostoucí .trn soubor

BLOKUJÍCÍ Kritika je oprávněná. Jeden stále doplňovaný soubor komplikuje retenci, obnovu i monitoring. Doporučení 1 backup = 1 fyzický soubor je vhodnější.

Výrok „ztráta souboru = ztráta celého řetězu“ je vhodné zpřesnit na: ztratí se všechny backup sety uložené na daném médiu, což může znemožnit pokračovat v point-in-time restore přes příslušné období.

N2b: CONTINUE_AFTER_ERROR

BLOKUJÍCÍ Z rutinního backup jobu odstranit. Standard má být:

WITH COMPRESSION, CHECKSUM

Silnější a přesnější argumentace je, že rutinní proces nemá normalizovat situaci, kdy CHECKSUM odhalí problém. Taková událost má být viditelný incident a má vyvolat diagnostiku.

4. N3 — denní FULL + týdenní DIFF

ZÁVAŽNÉ Dokument správně upozorňuje, že kombinace denní FULL + týdenní DIFF neposkytuje praktický recovery ani storage benefit.

VariantaSmysl
Týdenní FULL + denní DIFF + častý LOGÚspora místa, delší restore chain
Denní FULL + častý LOGJednodušší a kratší restore chain

Volba má být provedena až podle naměřené kapacity a požadovaného RTO.

5. COPY_ONLY

ZÁVAŽNÉ Pokud cílová strategie používá diferenciální zálohy, ad-hoc full backup produkční databáze používaný například pro NAV-TEST má být explicitně COPY_ONLY, aby neovlivňoval differential base.

BACKUP DATABASE [NAV-LIVE]
...
WITH COPY_ONLY, COMPRESSION, CHECKSUM;

Pokud se od diffů úplně ustoupí, tento konkrétní problém odpadá.

6. Opravený job — další technické výhrady

6.1 Název souboru

Časové razítko v návrhu má přesnost jen na sekundy. Pro běžný 15min schedule to většinou stačí, ale ruční spuštění nebo paralelní pokus může kolidovat. Doporučuji přidat milisekundy nebo jiný unikátní suffix.

NAV-LIVE_log_20260810_132015_437.trn

6.2 Ověření cílové cesty

Před prvním backupem musí rollout ověřit: existenci adresáře, write permission SQL Server service accountu a dostatek volného místa. Nemá to zůstat jen jako poznámka pod skriptem.

6.3 RESTORE VERIFYONLY

Po prvním ručním backupu nestačí pouze záznam v msdb.dbo.backupset. Doporučuji přidat:

RESTORE VERIFYONLY
FROM DISK = N'<novy_soubor>'
WITH CHECKSUM;

VERIFYONLY nenahrazuje skutečný restore test, ale je vhodný jako minimální rollout kontrola.

6.4 Dva úspěšné běhy nového jobu

Kontrola podle cílové cesty ve backupmediafamily neprokazuje přímo, že zálohy vytvořil konkrétní job. Robustní acceptance test má kombinovat SQL Agent job history + backup history + existenci fyzického souboru.

6.5 log_reuse_wait_desc

Požadavek, aby hodnota byla vždy NOTHING, je příliš absolutní. Krátkodobé jiné stavy mohou být legitimní. Vhodnější pravidlo je to, které už obsahuje cílový stav dokumentu: stav ≠ NOTHING déle než definovaný interval → alert.

8. RPO/RTO a log shipping

Jedna z nejsilnějších částí oponentury je správné oddělení technické možnosti od business rozhodnutí. IT může navrhnout například 15min log backupy, ale cílové RPO a RTO musí schválit vedení.

Log shipping nemá být prezentován jako alternativa k backupům. Je postaven na log backupech a přidává další recovery/availability mechanismus. Správná logika je:

backup strategie
+
volitelně log shipping

Licenční tvrzení o pasivním sekundáru doporučuji formulovat jako povinné ověření proti aktuálním Microsoft Product Terms a konkrétní licenční smlouvě, nikoliv jako kategorický závěr bez licenčního posouzení.
